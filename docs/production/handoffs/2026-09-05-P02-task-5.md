## Scope and implementation

- `when.resolve_time_context(envelope, now, resumed) -> TimeContext` preserves the captured reference in its IANA timezone. Unknown capture times never become observation-time captures. Per root's approved conservative interpretation, all observed-only relative scheduling requests ask for an exact date, including first-observed backlog. CLI/morning explicit captures retain their original reference. The existing Shortcut capture contract is unchanged; explicit Shortcut envelopes can supply a captured timestamp.
- ISO offsets, including negative offsets and Z, survive parsing. Zoneinfo round-trip checks reject DST overlaps/gaps unless an explicit offset supplies an instant. Numeric timestamps carry event and reminder dates through fixed JXA; date-only reminder components use the captured timezone. Guard past checks and overlap/duration arithmetic use timestamps, avoiding same-ZoneInfo fold comparison bugs. Hour/weekday checks use the request timezone. Date-only today is allowed; timed past requests are refused with no shift.
- Scheduler uses captured-reference date/zone in its prompt, validates simple today/tomorrow/yesterday resolutions, rejects recognized recurrence/compound requests and multi-action payloads, and requires raw-request duration/end evidence. Numeric/common-word duration evidence is checked against proposed interval length. Model-generated authorization or target fields are not copied into `Action`.
- Calendar/reminder destination resolvers return zero/one/many writable candidates with stable IDs. Unknown names never default; duplicate names ask. Defaults are resolved to a stable ID before persistence. Explicit `calendar-id`, `list-id`, and `reminder-id` lines in the current raw request select among matching candidates. IDs survive the durable payload and the in-memory action through completion and recovery. Completion of an existing recurring reminder is refused; the native completion script independently checks recurrence.
- Native reads require full EventKit authorization before requesting rows; reminder fetch timeout throws instead of returning `[]`. Calendar windows are bounded to 31 days; week summaries disclose event truncation and reminders disclose omitted counts. Calendar overlap checks include untitled events, reject missing event identity/time evidence, and compare actual intervals.
- A conflict question names title/start/end/calendar and supplies a local 16-character confirmation code. User restates the exact event and adds `confirm conflict <code>` as a separate line. The code is bound to event kind/op/title/start/end/stable destination/notes and current conflicting IDs/times. It is read from the current raw request only. This minimal explicit path is root-approved pending P03 conversational follow-ups.
- Executor runs fresh time, duration, target and overlap checks before new/PREPARED external effects, after APPLIED/APPLYING recovery branches. APPLIED repairs receipts; APPLYING reconciles exact references and never repeats a save. Legacy PREPARED actions lacking a bound target become NEEDS_REVIEW. Unknown outcomes remain review-required.
- Known pre-effect refusals use `WriteResult.needs_confirmation` and a `?` result marker, so the graph can deliver the actual question through the guarded Notes writer. This does not mark the action successful. A preexisting PREPARED intent is explicitly CANCELLED (`clarification_required`) before that delivery. Unknown outcomes and ordinary write/receipt failures remain `✗`; existing recovery tests still pass. Two fixed failure codes were added; SQLite schema remains 3.
- Index queries validate up to eight selected note IDs against live metadata. Changed notes are reread/redacted and metadata/permissions rechecked before returning a fresh 1,400-character excerpt. Private-title renames are excluded before body reads. Missing/unavailable/changed-again/budget-limited context omits stale content and carries an incomplete flag; writer/planner append a deterministic disclosure rather than depending on model compliance. No query-time embedding or persistent cache rewrite was added. This is up to eight selected-note validations, at most three Notes calls per changed note; not an eight-native-call total.
- Journal entries use actual explicit source capture dates only when the captured source covers those items. A CLI `file my dump` timestamp dates the command, not older thoughts. Unknown item capture dates are labeled `(filing date; capture date unknown)`. Existing durable filing plans retain rendered dates during recovery.

## Limits / review attention

- Native JXA/EventKit execution, numeric authorization behavior, Gregorian timezone component/alarm behavior and actual Apple IDs still require P06 signed-platform verification. Synthetic tests establish Python logic and generated fixed-source/data boundaries, not native permission correctness.
- External Apple/iCloud edits can race a checked overlap, metadata validation or Notes write. No transaction spans local ledger and Apple apps. No blanket exactly-once or permanently fresh answer claim.
- Fresh index validation covers selected query context, not every indexed note, and ranking still uses existing vectors. A changed note contributes its bounded opening excerpt without re-embedding; unavailable context is explicitly incomplete. Changes after that validation, including a delayed downstream checkpoint, are not an atomic freshness guarantee.
- Conservative English recurrence/compound/duration detection can ask extra clarifications (for example, conjunctions in a single title). This is not complete semantic understanding or multilingual intent verification.
- All observed-only relative Notes scheduling now asks once for an explicit date because original capture cannot be established. This is an intentional safety/usability tradeoff approved by root.
- Conflict approval requires a full restatement and code until P03 supports safer conversational references. The code is content binding, not a secret or authentication proof; user request text remains the authorization source under the existing product boundary.
- A canceled pre-effect action whose clarification receipt itself fails remains recorded/canceled; the graph may need review after a crash before a new checkpoint. It cannot automatically recreate that action. Failed ordinary writes and unknown external outcomes never become successful clarifications.
- New optional Action/State/WriteResult fields use defaults for older payloads. Old unbound PREPARED actions pause; known APPLIED receipt recovery remains possible. Do not downgrade/reset durable history to force execution.
- Default startup remains paused behind P06. Task 6 worker/lifecycle/migration work and all other production gates remain open. No merge, push, deployment or progress-ledger edits.
