## Outcome

- Replaced destructive runtime `undo.pop` with immutable `Snapshot(snapshot_id, before_html, after_revision, operation_id)`, non-destructive `peek`, and identity-checked `consume`.
- Encrypted undo keeps note IDs at its top level. Each note has a committed slot and, only while a write is in progress/uncertain, a staged preimage. The staged preimage is saved before the Notes mutation; required backup failure prevents the mutation. Verified success promotes it. Known refusal or controlled failure before mutation discards only that operation's staged preimage and preserves the previous committed snapshot.
- Unknown/crashed effects retain their exact preimage. `peek` exposes an unresolved staged snapshot as recovery-only (no authoritative post revision). Further ordinary writes cannot overwrite that unresolved backup. Reconciliation through the existing durable ledger promotes the matching backup after body evidence matches, without repeating the external write.
- Restore requires the exact note-bound snapshot ID, stored successful post-write revision, and exact saved HTML. Only a deterministic fixed receipt/tag-tick transformation is permitted when explicitly requested by the restore Write. Matching a newly captured live revision alone cannot authorize an old restore. Arbitrary HTML or a different snapshot is refused.
- Snapshot identity is checked again at the final mutation boundary, before final policy/source/operation checks. No user text is stripped to fabricate revision equality. A freshly typed `@notron undo` therefore counts as an intervening edit and offers a recovery copy.
- Restore consumes only after the observed restored body is verified. Its receipt is included in that one restore, so the slot is not refilled. Failed, divergent, crashed, or snapshot-consume-failed restores retain the snapshot. Replaying a persisted verified restore finishes consumption without writing again; stale consumption cannot delete a newer slot.
- Recovery copy confirmation is the exact tagged command `@notron undo recovery copy <snapshot-id>` in the source note. It requires that same live unique command anchor, current saved snapshot identity, exact text projection, and deterministic destination title. Generic yes, wrong snapshot IDs, removed confirmation, and stale snapshots do not authorize creation.
- Copies go through Executor creation. The source receipt is a fixed, snapshot-bound insert that requires the matching creation operation to be durably verified. Creation failure stops before that receipt. Neither recovery offers nor recovery receipts replace the original undo slot. Recovery creation does not grant automatic filing-home permission: existing new-note policy governs accessibility until the user makes a separate library choice. No policy registration occurs in the flow, so verified creation/receipt operations and the graph request reach their proper terminal states without a policy-purge exception.
- Every nonblank recovered line is deterministically marked as inactive history, preserving readable words/tag spelling while preventing historical commands from becoming fresh requests in the copied note. This applies even when tags emerge from Markdown rendering or appear in mixed list/multiline blocks. Producer and Executor require the same marked projection.
- Dry-run restore/copy paths preserve Notes and snapshot content. Ask-note undo still asks for the intended source note and preserves any existing Ask snapshot.

## Storage and migration

New storage shape is `{note_id: {current: Snapshot | null, pending: Snapshot | null}}` inside existing AES-GCM storage. At most one committed and one unresolved staged preimage per note; this is not an accumulating history. Ignore/deletion retention still removes the entire note-keyed entry, including pending content. Missing/wrong storage keys, authenticated encryption, legacy plaintext rejection, and existing delete/ignore cleanup remain covered.

Existing encrypted string bodies remain readable as recovery-only snapshots with deterministic identities and no invented post-write revision. Calling `save(note_id, old_body)` without operation/revision evidence likewise records recovery-only content for legacy/test callers. Empty preimages are preserved for real operation-bound writes. No plaintext fallback or automatic real-data migration was introduced. Snapshot identifiers use hyphens so confirmation commands do not trip the existing long-hex credential filter.

## Limits / review focus

- Apple Notes remains a non-atomic full-body API. External editor/iCloud changes in the final read/write gap can still be overwritten without detection. Local serialization and snapshot checks do not establish native CAS or multi-device safety.
- Recovery copies are a text-only projection rendered using the existing Markdown/Notes renderer; unsupported embedded Apple objects are not recreated. Existing Guard title/size/secret filtering still applies to new recovery copies. The encrypted preimage remains available even if copy creation is refused.
- Legacy/uncertain snapshots never permit direct overwrite. An unresolved staged backup intentionally blocks further ordinary mutations until verified reconciliation; a recovery copy itself does not assert that an uncertain original write succeeded.
- The pre-existing tagged-line granularity limitation for mixed tagged/untagged list blocks remains; this task preserves the prior deterministic tick policy rather than redesigning conversation parsing.
- Native Notes, Keychain, permissions, crash-kill, iCloud, and signed startup behavior were not exercised. The P06 gate remains unchanged. No merge, push, app writes, migration, listener startup, deployment, or release-readiness claim.
- Python, SQLite ledger, AES-GCM sensitive storage, existing Apple Notes adapter. No AI model is invoked by undo, restore, confirmation, or the executor; provider/model configuration is unchanged.
